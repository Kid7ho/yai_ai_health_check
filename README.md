# 건강정보 확인 — 카카오톡 채널 기반 건강정보 검증 서비스

어르신이 카카오톡으로 받은 건강정보를 채널에 공유하면, 학술 논문과 식약처 공공데이터로
이중 검증해 4단계 신호등 결과를 돌려준다. 새 앱을 설치하지 않고, 늘 쓰던 카카오톡 공유
동작에 한 단계만 더한다.

연세대학교 인공지능 학회 YAI 산학협력 과제. 학술 검색은 Liner Academic Search API를 쓴다.

**대상 범위는 음식 · 식품 · 건강기능식품 정보로 한정한다.** 의약품, 시술, 질병 진단은
범위 밖이며 서비스가 명시적으로 거부한다.

이 서비스는 진단하지 않는다. 모든 응답에는 "이 결과는 참고용이며 진단이 아닙니다"가
구조적으로 항상 포함된다.

## 판정 결과

| 라벨 | 어르신에게 보이는 문구 |
|---|---|
| `TRUSTWORTHY` | 믿을 만해요 |
| `CAUTION` | 조심하세요 |
| `WARNING` | 주의하세요 |
| `UNKNOWN` | 알 수 없어요 |

어느 규칙에도 확실히 맞지 않으면 무조건 `UNKNOWN`이다. 잘못 판정하는 것보다 판정을
보류하는 편이 훨씬 안전하다.

## 실행

```bash
uv sync --extra dev     # uv가 없으면: python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
uv run pytest           # 전체 테스트
uv run pytest tests/golden -v    # 골든셋만
uv run uvicorn healthcheck.api.app:app --reload    # 스킬 서버 (Fake 어댑터)
```

## 디버그 채팅 화면

카카오톡 채널에 붙이기 전에 실제 데이터를 넣어 보며 동작을 확인하는 도구다.
서버를 띄우고 <http://127.0.0.1:8000/debug>를 열면 된다.

- 카카오톡처럼 생긴 채팅창에 유튜브 링크나 건강정보 문장을 넣는다
- 실제 카카오에 나갈 카드와 면책 문구가 그대로 렌더링된다
- 오른쪽 패널에 파이프라인 중간 산출물이 전부 나온다. 자막, 뽑아낸 주장,
  식약처 인정 정보, 논문 목록과 찬반, 판정 입력값, 매칭된 규칙 ID,
  단계별 소요 시간, 그리고 카카오 ack·콜백 페이로드 원문
- `live`와 `fake`를 골라 쓴다. `fake`는 외부 API를 부르지 않으므로 규칙만
  시험할 때 Liner 토큰을 아낀다

제품 화면이 아니라 개발 도구다. 배포할 때는 `DEBUG_UI=0`으로 끈다.

컨테이너로 띄울 때는 `docker build -t healthcheck . && docker run -p 8000:8000 healthcheck`.

스킬 서버는 `POST /skill`에서 카카오 요청을 받고 `GET /health`로 규칙표 버전과
대기 중인 작업 수를 돌려준다. 키가 없으면 Fake 어댑터가 붙으므로 지금 바로 띄워
동작을 볼 수 있다.

## 외부에 노출할 때 반드시 할 것

스킬 서버는 공개 https 주소로 노출해야 한다. 인증이 없으면 주소를 아는 누구나
파이프라인을 호출하고, Liner 토큰이 남의 요청에 쓰이며, 큐가 차서 어르신 요청이
밀리고, 저장소에 무관한 기록이 쌓여 목표 지표가 오염된다.

1. `.env`에서 `DEBUG_UI=0`으로 디버그 화면을 끈다
2. 아래 둘 중 최소 하나를 켠다

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"   # 토큰 생성
```

`SKILL_AUTH_TOKEN`에 넣으면 그 값이 담긴 헤더가 없는 요청을 거부한다. 헤더 이름은
`SKILL_AUTH_HEADER`로 바꿀 수 있다. 오픈빌더가 임의 헤더를 지원하지 않으면
`SKILL_PATH`를 추측하기 어려운 경로로 바꾼다. 그 경로 전체가 스킬 URL이 된다.

`GET /metrics`도 같은 토큰으로 보호된다. `GET /health`는 외부 감시 도구가 호출할
수 있어야 하므로 열어 둔다.

## 골든셋 측정

이 프로젝트의 품질 기준은 스펙 구현 여부가 아니라 골든셋 통과 여부다.

```bash
python scripts/measure_golden.py              # 실제 API로 전 구간 측정
python scripts/measure_golden.py --mode fake  # 토큰 안 씀
uv run pytest tests/golden                    # 규칙 엔진 회귀 검증 (네트워크 없음)
```

두 가지를 구분한다. `tests/golden`은 `판정입력`이 적힌 케이스만 돌려 규칙 엔진을
회귀 검증한다. `measure_golden.py`는 원문에서 시작해 ③ 구조화와 ④ 검증까지 전
구간을 재므로 외부 API를 쓴다.

현재 23건 모두 일치한다. 다만 기대 라벨이 개발자 판단이며 의료 자문의 검수를
받지 않았다. 검수 후 값이 바뀌면 그것이 정답이고 숫자도 다시 재야 한다.

## 고시형 원료 목록 교체

고시형 기능성원료의 기능성 문구는 공개 API로 받을 수 없다. 오픈API I-0040과
I-0050은 모두 개별인정형이고, 법제처 API로 받는 고시 본문은 표를 첨부파일로
넘긴다. 그래서 사람이 공전 첨부파일에서 표를 뽑아야 한다.

표를 확보하면 손으로 YAML을 쓰지 말고 변환 도구를 쓴다. 오타가 판정에 바로
영향을 주기 때문이다.

```bash
python scripts/import_notified.py 공전표.tsv --dry-run   # 먼저 확인
python scripts/import_notified.py 공전표.tsv             # 규칙 파일 생성
```

표에 필요한 열은 원료명과 기능성내용 둘이다. 효능 대상은 기능성 내용에서
자동으로 뽑는다. 뽑지 못한 원료는 경고로 알려 주며, 그 원료는 일치도 비교가
되지 않아 판정이 보류된다. 그때는 `rules/claim_patterns.yaml`의 효능 대상
목록에 그 표현을 추가한다.

생성 후 의료 자문의가 공전 원문과 대조하고 파일의 `검수완료`를 `true`로 바꾼다.

## 자막 확보 현황 검증

어르신이 받는 영상에 자막이 실제로 얼마나 있는지 재는 스크립트다. 이번 MVP는
자막이 있는 영상만 지원하므로, 이 비율이 서비스가 답할 수 있는 비율의 상한이다.

```bash
python scripts/check_transcripts.py samples/videos.txt --claims
python scripts/check_transcripts.py samples/videos.txt --json 결과.json --interval 3
```

영상 목록은 한 줄에 하나씩 적는다. 주소 뒤에 설명을 붙여도 되고 `#`은 주석이다.
`--claims`를 주면 자막에서 뽑아낸 주장까지 보여 준다. 규칙 기반 추출이 실제
자막에서 어디까지 되는지 재는 용도이며 네트워크를 더 쓰지 않는다.

같은 IP에서 몰아 부르면 YouTube가 차단한다. 차단이 감지되면 즉시 멈추고 남은
항목을 미확인으로 표시한다. 차단이 있었으면 종료 코드가 2다.

## 규칙표 검수 (의료 자문의용)

판정 논리는 코드에 없다. `rules/verdict_rules_v0.yaml` 한 파일에 있다.
코드를 읽지 않아도 이 파일만 보고 검수하고 수정 의견을 줄 수 있게 만들었다.

| 파일 | 내용 |
|---|---|
| `rules/verdict_rules_v0.yaml` | 판정 규칙 12건. 위에서 아래 순서로 평가 |
| `rules/claim_patterns.yaml` | 질병 치료 표현, 효능 표현, 범위 밖 표현 목록 |
| `rules/ingredient_aliases.yaml` | 성분명 정규화 사전, 영문 검색어 |
| `rules/notified_ingredients.yaml` | 고시형 기능성원료 목록 ⚠ 검수 전 초안 |
| `rules/response_guard.yaml` | 응답에 쓰면 안 되는 진단·처방 표현 |
| `rules/ad_violation_patterns.yaml` | 법으로 금지된 광고 표현 ⚠ 법률 검토 필요 |
| `rules/brand_names.yaml` | 근거 화면에 표시할 브랜드 씨앗 목록 |
| `rules/authority_roles.yaml` | 근거 화면에 표시할 전문가 역할 표현 |
| `rules/stance_patterns.yaml` | 논문 찬반 판정 표현, 제외할 문헌 |

수정 의견은 규칙 ID(`R-0xx`)를 적어 주면 된다. 판정 로그에는 사용된 규칙 버전과
매칭된 규칙 ID가 함께 남으므로, 어떤 판정이 왜 나왔는지 나중에 되짚을 수 있다.

## 저장하는 데이터

사용자가 보낸 원문과 카카오 사용자 키를 저장하게 된다. 무엇을 저장하고 얼마나 두는지
처음부터 정해 둔다.

| 항목 | 예시 | 왜 저장하는가 | 보존 기간 | 익명화 |
|---|---|---|---|---|
| 공유 원문 텍스트 | "블루베리로 당뇨 완치" | 판정 근거, 오정보 유형 집계 | 90일 | 개인 식별 정보 아님 |
| 유튜브 링크·영상 ID | `youtube.com/watch?v=…` | 캐시 키, 반복 요청 식별 | 무기한 | 해당 없음 |
| 자막 텍스트 | 영상 자막 원문 | 추출 캐시, 재판정 | 90일 | 해당 없음 |
| 카카오 사용자 키 | 채널별 익명 식별자 | 콜백 전송 대상 식별 | 30일 | 30일 후 해시로 대체 |
| 판정 결과·규칙 ID·규칙 버전 | `WARNING` / `R-021` / `v0` | 역추적, 품질 개선 | 무기한 | 사용자 키 분리 저장 |
| 누적 확인 건수·오정보 유형 수 | 집계 숫자 | 사업 목표 지표 | 무기한 | 집계값만 |

원칙 세 가지.
- 카카오 사용자 키는 콜백 전송에만 쓰고, 보존 기간이 지나면 해시로 바꾼다
- 보존 기간 필드를 스키마에 처음부터 둔다. 만료 삭제를 나중에 붙이지 않는다
- 이름, 전화번호, 주소는 어떤 경로로도 저장하지 않는다

만료 처리는 행을 지우지 않는다. 만료된 열만 비우고 사용자 키는 해시로 바꾼다.
누적 확인 건수와 오정보 유형 수가 목표 지표이므로 집계는 유지되어야 한다.

```bash
python scripts/purge_expired.py     # 하루 한 번 실행을 전제로 만들었다
```

지표는 `GET /metrics`로 확인한다. 집계값만 담고 개인을 식별하는 값은 넣지 않는다.

## 구조

```
rules/                  판정 규칙표와 표현 사전 (YAML, 자문의 검수 대상)
src/healthcheck/
  domain/               라벨과 파이프라인 단계 간 타입
  ports/                외부 의존성 인터페이스 (구현 없음)
  adapters/fake/        키 없이 테스트를 돌리기 위한 Fake 구현체
  pipeline/             ① 입력 → ② 추출 → ③ 구조화 → ④ 검증 → ⑤ 판정 → ⑥ 응답
  storage/              리포지토리 패턴, SQLite
  api/                  FastAPI 스킬 서버, 비동기 워커
tests/
  unit/                 규칙 엔진 단위 테스트
  golden/               골든 테스트셋. 이 프로젝트의 품질 기준
```

세션 맥락과 설계 제약은 [CLAUDE.md](CLAUDE.md)에 정리해 두었다.
